# OPFS-first Project Store, File System Access as a capability upgrade

> **Amended by [ADR-0024](./0024-backup-and-handoff-are-different-artefacts.md):** the OPFS root holds **several named workspaces** rather than being one, so that a Review Workspace is not a subdirectory of the user's own. `OpfsProjectStore` already takes a directory-handle factory, so this changes what is passed in and not the store. ADR-0024 also requires `navigator.storage.persist()`, which is called nowhere today — OPFS data is otherwise best-effort and evictable, which is unacceptable now that it is the primary home for a shared pool of large pyramids ([ADR-0023](./0023-historical-maps-and-alignments-live-in-the-workspace.md)).
>
> **The "explicit zip operation" below is now a tar**, and it is a whole-workspace backup rather than a per-project handoff — see ADR-0024 for why the zip could not carry it.
>
> **And the choice between backings is no longer first contact.** This ADR's own principle is that a folder workspace is a capability upgrade and never a gate; the hub asked the question anyway. It moves into workspace settings, with browser storage as the silent default.
>
> **Amended by ticket 20: user bytes may sit briefly in `localStorage`, outside the ProjectStore.** ADR-0017 rule 3 was measured to be false for a real navigation, and the only synchronous durable write a page has is `localStorage` — so a **write-ahead journal** holds an edit's bytes between the moment it is made and the moment the store's asynchronous write lands. That is a genuine exception to the sentence below and it is named here rather than left to be discovered. What it is *not* is set out in "The one exception, and its exact size" below and in [ADR-0017](./0017-autosave-semantics.md).

All project data (IIIF tiles, `info.json`, annotations, manifests) is read and written through a single narrow `ProjectStore` interface — `read(path)`, `write(path, bytes)`, `list(prefix)`, `delete(path)`. The first and default implementation targets the **Origin Private File System (OPFS)**, which is supported in every modern browser. A second adapter targets the **File System Access API** (`showDirectoryPicker`) so a user can point a project at a real folder they can back up, Dropbox-sync, or commit to git.

We chose OPFS-first rather than File System Access-first even though the visible folder is the headline feature of the design. File System Access is Chromium-desktop-only (~28.6% global; Firefox has declared it "harmful" and will not ship it; Safari desktop and iOS do not support it; Chrome Android does not support it). Had we built against the directory picker first, the abstraction would have been shaped around one backend and the cross-browser fallback would have rotted, because day-to-day development happens in Chrome. Building OPFS first forces the interface to be honest and makes import/export a first-class path from day one.

## The one exception, and its exact size

The sentence above — every byte of a user's work goes through one narrow `ProjectStore` — is what makes a scholar's project a directory of files they own rather than rows in somebody's database, and it should not be qualified lightly. Ticket 20 qualifies it exactly once.

An edit is written to the store asynchronously, on a debounce (ADR-0017 rules 1 and 2). Between the keystroke and the write landing there is a window in which the bytes exist only in memory, and a document being unloaded does not run the continuation that would write them. The **write-ahead journal** closes that window by keeping the pending bytes in `localStorage`, synchronously, and replaying them into the store at the next startup. It lives in `packages/core/src/autosave/journal.ts`; the replay is `replay.ts`. ADR-0017's "Rule 3, amended" holds the measurement.

**What the journal is not**, because every one of these would be a worse decision than the one taken:

- **Not a store.** Nothing reads a Project out of it. No path in the application resolves through it, and the viewer does not know it exists. It holds only files the store has **not** taken: an entry is removed the moment its write lands, so in ordinary use it is empty between one keystroke and the next.
  - ⚠ **It is not guaranteed to be empty, and an earlier draft of this bullet claimed it was.** An entry whose write *failed* is kept on purpose, so an unplugged drive costs a delay rather than the edit; and an entry belonging to a Workspace the user never opens again persists until they say otherwise. Those two are exactly why `journalledWorkspaces` and `discardJournal` exist, and why Workspace settings reports orphans (see below). Saying otherwise here would have made this section's one job — being accurate about what the journal is not — false in the direction that hides unbounded growth.
- **Not a backup.** ADR-0024's tar is the backup. The journal holds no history, nothing that has already been written, and nothing belonging to a Workspace other than the one it names.
- **Not durable.** Clearing site data takes it, a private window closing takes it, and a browser evicting the origin takes it. `navigator.storage.persist()` (ADR-0024) covers it along with everything else, and a refusal there is already reported in Workspace settings. A browser that will not give the page `localStorage` at all gets no journal and is **told so** rather than left to assume it has one.
- **Not a second writer.** The replay goes back through the same `ProjectStore.write` — atomic, temp-then-rename (ADR-0017 rule 4) — and an Alignment goes through `alignment/alignment-file.ts` like every other Alignment write (ADR-0023, ticket 18).

**Orphans are reported and never swept up**, and that is a decision rather than an oversight. A replay only ever looks at the Workspace being opened, so an entry naming one that has gone would sit in `localStorage` for ever with nothing that could ever meet it — the unbounded growth the "not a store" bullet above has to be honest about. Workspace settings therefore lists them and offers a discard. It stops short of discarding for the user, because "not in `listOpfsWorkspaces`" is not "gone": a folder Workspace never appears in that list at all, and neither does a browser Workspace on a listing that happened to fail. Throwing away somebody's unsaved edit on that inference would be the silent loss this whole epic is about, arriving through the tidying-up.

**And it is keyed by Workspace**, because since ticket 12 the OPFS root holds several and one click on the bar switches between them. An edit typed into "Marking 2026" replays into "Marking 2026" and nowhere else. The key carries the backing too, so a folder called `Marking 2026` and a browser Workspace of that name are not confused for one another. The residual gap is that a picked folder has no stable identifier a page may keep, so two folders with the same name share a key; the replay's own preconditions bound it, and it is stated in ADR-0017 rather than left in the code.

## Consequences

- The first thing built is zip import/export, before anything is visible on screen. Accepted.
- Firefox/Safari/iPad users get a fully functional authoring tool whose project lives in invisible browser-managed storage; moving data in or out is an explicit zip operation.
- Chromium desktop users additionally get "put this project in a real folder," which is what makes the git-publish and Dropbox-backup stories work.
- Persisting a chosen directory across visits requires storing the `FileSystemDirectoryHandle` in IndexedDB and calling `requestPermission()` on return; true no-prompt persistence needs Chrome 122+.
