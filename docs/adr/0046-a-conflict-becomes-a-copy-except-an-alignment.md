# A conflict becomes a copy, except an Alignment

One file changed on both sides of the Synchronization Baseline is a **Conflict**. There is no honest
automatic resolution for one, and there never will be: merging two GeoJSON annotation sets or two
Alignments of one sheet produces a document neither scholar wrote. So Ballastella does not merge and
does not choose. What it does instead is make sure both versions survive somewhere a scholar can look
at them.

## Only three kinds of file can conflict

Of everything a Sync moves, most of it cannot be contested at all. Tiles under `images/**` and
`base-map/tiles/**` are written once when a Map Image is ingested or a Base Map is taken offline and
are never edited afterwards. `ballastella-site.json` is regenerated by every Sync from the Projects
that exist. So the conflict problem is three file kinds, not a tree of forty thousand:

| Contested file | Becomes |
| --- | --- |
| `<project>/annotations/<layer-id>.geojson` | another Layer in the same Project, new id, named `<layer name> (from GitHub)` |
| `<project>/project.json` | another Project, `<name> (from GitHub)`, off the Front Page |
| `alignments/<image-id>.json` | nothing — the author is asked which to keep |

**Resolution happens at the coarsest contested unit.** Where `project.json` is contested the whole
Project doubles and its individual Layers do not also double; otherwise a Project with three contested
layers yields a duplicate Project *and* three duplicate Layers, and the scholar has six things to read
where two would have done.

**A copy exists on both sides.** It is made in the Workspace and sent in the same Sync, so the machine
that wrote the other version gets it on its next get, and both scholars see both versions. A Conflict
Copy that lived on one machine would leave the two people looking at different libraries and
disagreeing about what happened.

## The Alignment is the exception, and it is the whole reason for the exception clause

There is exactly one Alignment per Map Image, keyed by the image's id
([ADR-0023](./0023-map-images-and-alignments-live-in-the-workspace.md)). A second file at
`alignments/<image-id> (from GitHub).json` is referenced by nothing and drawn nowhere: it is a copy
the scholar cannot look at, which is strictly worse than being asked a question. So an Alignment
Conflict stops at that one Map Image and asks — **keep mine** or **take the one from GitHub** — showing
each side's control-point count and when it was made. The rest of the Sync proceeds around it.

Producing a duplicate **Map Image** to carry the second Alignment was considered. It is the only shape
that would make both visible, and it costs a second identity for one sheet, which then propagates: two
entries in the Map Image list, two thumbnails, and a Project that can accidentally reference both. The
question is cheaper and the answer is one the scholar already has.

## Why the Sync does not simply stop

Stopping the whole operation on any Conflict — changing neither side — is the safer-sounding rule and
it is refused. A Sync moves gigabytes; a single contested `annotations/layer-3.geojson` would block all
of it, every time, until somebody resolved a thing they may not want to resolve today. Worse, the
scholar's remedy would be to press **Overwrite the repository**, which is the one destructive control
in the product, and to be trained to press it by an obstruction they cannot otherwise clear.

Everything that can move safely moves in both directions instead, and the badge tells the truth
without extra machinery: a Sync that made Conflict Copies has not brought the two sides into
agreement, so it does not read **in sync**, and it keeps saying there is work outstanding until the
scholar has deleted one of each pair.

Three-way merging `project.json`, GeoJSON, and Alignments was rejected outright, and remains rejected.
Deleting one of two things you can both see is a scholarly judgement; producing a third thing neither
scholar wrote is not.
