# Workspaces are a roster, not a settings dialog

> **Amends [ADR-0001](./0001-opfs-first-project-store.md)** on where the backing question is asked and on how many folder Workspaces there may be, and supersedes the deliberate arrangement of the Workspace settings dialog — its three groups, its persistence sentence, its retention of backup, restore, the other-Workspaces list and the install offer, and its accessible name — which this ADR removes rather than rearranges.

A scholar who had ever chosen a folder could not get away from it. `awaitingFolder` is `backing === 'browser' && reopenable !== null`; `reopenable` is filled on every load from a single IndexedDB slot and `#adopt` preserves it verbatim through a switch, so switching to a browser Workspace never cleared it. The only control that cleared it, *Use browser storage instead*, was rendered only while `backing === 'folder'` — false in exactly the state it would have fixed. So the offer to reopen stood on the hub for ever, in six non-dismissible renderings, and worse: `ProjectScreen` and the align route both computed `recovering = session.status === 'unreachable' || storage.awaitingFolder` and drew the notice **instead of the screen**, so a merely-remembered folder made every Project in every Workspace unopenable. That is the failure this ADR exists to remove, and none of it was a wrong local decision — it is what a single-folder mode does when the rest of the model became plural around it.

**A folder is a kind of Workspace, not a mode the application is in.** There may be several, listed in one switcher beside the browser-backed ones, each opened by picking it — which still costs a gesture, because a browser grants a directory only when the user asks and guessing would be a silent switch into somebody else's files. `awaitingFolder` ceases to exist: a folder that is not open is simply not the one that is open, which is what every other row in the list already means. `unreachable` survives, and only for a Workspace that breaks while the author is inside it. The route guards go with the concept.

**A folder Workspace is keyed by a minted reference, never by its folder's name.** `folder:<folderName>` is `handle.name` — the last path segment — and five durable record families hang off that one key: the write-ahead journal, interrupted deletions, publish manifests, the Remote relationship with its Synchronization Baseline, and the local-change index. Two folders called `maps` on two drives were one key, bounded only by there being one folder at a time; plural, the collision is reachable in a single session, and `deleted-projects.ts` already records the asymmetry — a wrong-Workspace replay costs one overwritten file the author is told about, while a wrong-Workspace deletion would list a directory and remove every byte in it. The Remote binding and Baseline are bounded nowhere at all. The mechanism is already in the tree: `retainWorkspaceFolder` mints `retained:<uuid>` handles into the same object store, and `ReviewOrigin` carries a `folderReference` beside its `workspaceKey` for precisely this reason — *"a display name is not identity, and for a folder it is barely a hint."* A one-time migration moves the existing single `folder:<name>` records when that folder is next opened.

**And a folder Workspace gets a name of its own**, stored beside its reference, with the directory's actual name shown beneath it. This overturns the standing rule that a Workspace's name is its directory name in both backings — the rule the OPFS naming module still states, and which `CONTEXT.md`'s **Workspace** entry assumes. It was right while there was one folder and is unworkable with several: two folders called `maps` are two identical rows, and the browser offers the page no path to tell them apart with.

**The backing question returns, at creation, and stays barred from first contact.** ADR-0001's amendment moved it out of first contact because a folder is a capability upgrade and never a gate, and a first-time author cannot answer it. That reason is untouched: the first Workspace still appears silently, browser-backed, with nothing asked. **New Workspace…** is a deliberate act by somebody who already has one, so the choice there is not a gate. Where the File System Access API is absent the choice is not offered and the *kind* is never named — a Workspace is simply a Workspace — while the eviction warning is stated as an ordinary fact about this one, with no implication that another sort was available. Hiding the choice is right; hiding the risk would be the loss ADR-0024 exists to prevent.

**Workspace settings is deleted, and nine capabilities are re-homed rather than lost.** They had no second entry point anywhere: Backup and Restore, Workspace deletion with the only report of a Workspace's size, write-ahead journal orphans and their discard, the PWA install offer, what the browser said about keeping the work, converting a browser Workspace into a folder, unbinding a Remote, the legacy-binding question, and opening any public repository by typed address. The split is by subject. The **switcher becomes a roster** — each row opens, renames or deletes, because a Workspace is deleted from the list of Workspaces. **Workspace Home** takes Backup, Restore, the install offer, the storage warning and the journal orphans, because those are about the Workspace the author is in. The three GitHub items go to the one door (ADR-0041). And converting is renamed to what it is — **Move this Workspace into a folder…** — which has to survive, because `restoreFrom` and `openFromGitHub` are both documented *"always a browser-storage Workspace, whatever the current backing is"*: without it, and with folders creatable only as new, there would be no way at all to get existing work onto disk.
