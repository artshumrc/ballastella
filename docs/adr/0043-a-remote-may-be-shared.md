# A Remote may be shared

> **Amends [ADR-0033](./0033-a-publish-mirrors-an-owned-namespace.md) and [ADR-0038](./0038-workspace-synchronization-is-explicit-and-baseline-based.md).** Neither is wrong; both were written where a Remote had one author.

Collaboration works, and it needs nothing built to allow it. GitHub documents that a user access token reaches *"repositories they own, repositories where they are a collaborator, and repositories that they can access through an organization membership"*, and that an App acting for a user reaches the intersection of what the App may touch and what the user may touch — *"if you have access to repositories `A` and `B`, and the GitHub App has access to repositories `B` and `C`, then the app can only access repository `B` when acting on your behalf."* So a write collaborator signs in, the repository is simply in their list, and they publish to it with `Contents: write` and no admin: they install nothing, visit no installation screen, and need no organisation owner, because *"an app does not need to be installed in order for a user to authorize the app."*

**The asymmetry is the design.** Bringing a repository into an installation is an admin-only act — the endpoint that would do it needs repository admin and rejects every App token — while *using* one is not. So the onboarding difficulty ADR-0040 is about is confined to the first person to bring a given repository in, and everyone after them meets none of it. Two consequences follow. A repository missing from an author's listing branches on whether they are its admin: an admin is offered the preselect deep link, and a non-admin is told to ask the repository's admin, rather than being sent to a screen where they can accomplish nothing. And the per-repository `permissions` the listing already returns decides whether a publish affordance is offered at all, so a read-only collaborator never presses a button that will refuse them.

**Publish anyway is the one control whose blast radius is somebody else's afternoon.** ADR-0038 keeps it as the explicit local-wins escape hatch, and on a solo repository local-wins can only ever discard the author's own work. On a shared one it means deleting a collaborator's, because a Publish mirrors an owned namespace and removes what the local Workspace does not have (ADR-0033). The inbound direction has refused to delete unnamed work since `UpdateDeletionPreview`; the outbound direction never needed to. It does now. Where the Remote is not solely the author's — its owner is not the signed-in account, or GitHub reports other contributors — **Publish anyway names what it would remove and requires that confirmation**, in the shape the inbound preview already has.

**And the limit is stated rather than met as a Conflict.** ADR-0024 refuses merges outright: *"there is no honest resolution for two Alignments of one sheet."* So collaborators work comfortably on different Projects in one Workspace and cannot both align the same Map Image — the second one meets a Conflict that stops without changing either side. That is the boundary of what collaboration means here, and it belongs in what the interface says up front, not in a refusal discovered at the end of an afternoon.

**A pull-only relationship says only what is known.** Hydrating from a public Remote records the binding, and push rights cannot be read without a credential. Signed out, the door says publishing needs a sign-in and nothing about rights. Signed in with push absent, it says the author may take changes from the repository but not publish to it, and its primary action becomes publishing to a repository of their own. What must never happen is the badge reading *Changes to publish* as an invitation into a refusal.

**One repository, public, and no private Remote.** Supporting a private repository as backup-without-a-site would mean threading a credential through a hydrate path built to send none, making Pages conditional, and explaining to an author why their address answers nothing. It is a second product and it is fenced here rather than left implied — which is the other reason the interface never calls a Remote a *backup* (ADR-0024 reserves that word for the tar): *backup* promises this Workspace restored, and what a Remote gives is a new Workspace hydrated from it.
